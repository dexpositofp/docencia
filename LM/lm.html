1. Introducción a los Lenguajes de Marcas

¿Qué son y para qué sirven?

Un lenguaje de marcas (o lenguaje de marcado) es un sistema que utiliza etiquetas o marcas especiales para añadir estructura y significado a un contenido de texto. Estas marcas indican qué es cada parte del contenido: un título, un párrafo, una lista, una fecha, un precio, etc.

Los lenguajes de marcas sirven para:

  • Estructurar información: organizar datos de forma jerárquica y clara
  • Dar semántica: indicar el significado de cada parte del contenido
  • Facilitar el procesamiento automático: las máquinas pueden entender y manipular los datos
  • Separar contenido de presentación: el contenido (marcado) se separa del diseño visual (CSS)
  • Intercambiar información: diferentes sistemas pueden comunicarse usando formatos estándar

Concepto clave: Un lenguaje de marcas describe qué es cada dato, mientras que otras tecnologías determinan cómo se ve (CSS) o cómo se comporta (JavaScript).

Diferencia entre lenguaje de marcas y lenguaje de programación

Es fundamental entender que un lenguaje de marcas NO es un lenguaje de programación:

Característica Lenguaje de Marcas Lenguaje de Programación
Propósito Describir y estructurar información Crear algoritmos y lógica computacional
Ejecución No se ejecuta, se interpreta/renderiza Se compila o interpreta para ejecutar instrucciones
Variables No tiene variables (salvo plantillas) Puede declarar y manipular variables
Control de flujo No tiene bucles ni condicionales Tiene if, for, while, switch, etc.
Cálculos No realiza operaciones matemáticas Puede sumar, restar, multiplicar, etc.
Ejemplos HTML, XML, Markdown, LaTeX JavaScript, Python, Java, C++

Error común: Decir "programar en HTML" es incorrecto. Lo correcto es "escribir HTML" o "maquetar con HTML". HTML no programa, describe.

Por qué son fundamentales en desarrollo web y programación

Los lenguajes de marcas son absolutamente esenciales en tu carrera como desarrollador:

  • Desarrollo web: HTML es la base de toda página web; sin él no existe la web moderna
  • Configuración de aplicaciones: XML/YAML/TOML se usan para configurar frameworks (Spring, Maven, Docker, Kubernetes)
  • APIs y servicios web: JSON y XML son los formatos estándar para intercambiar datos entre aplicaciones
  • Documentación técnica: Markdown es el estándar de facto para README, wikis, y documentación de proyectos
  • Bases de datos: Muchas BBDD (como MongoDB) almacenan datos en formato JSON/BSON
  • Publicación académica: LaTeX es el estándar para artículos científicos y tesis técnicas

Realidad profesional: Como desarrollador Full Stack, usarás lenguajes de marcas TODOS LOS DÍAS: HTML para interfaces, JSON para APIs, Markdown para documentación, YAML para CI/CD, etc.

2. XML (Extensible Markup Language)

Para repasar: Antes de adentrarte en XML, asegúrate de entender:

  • Qué es un lenguaje de marcas (visto en introducción)
  • La diferencia entre lenguaje de marcas y lenguaje de programación
  • Conceptos de estructura jerárquica (padre-hijo, árbol)

Conceptos básicos

XML (eXtensible Markup Language) es un lenguaje de marcas diseñado para describir, almacenar e intercambiar datos de forma estructurada. A diferencia de HTML, XML no tiene etiquetas predefinidas: tú defines las etiquetas según tus necesidades.

¿Qué significa "extensible"?

La palabra "extensible" en XML significa que TÚ puedes crear tus propias etiquetas según lo que necesites describir. No estás limitado a un conjunto fijo de etiquetas como en HTML.

HTML (etiquetas fijas):

<!-- Solo puedes usar etiquetas predefinidas -->
<h1>Título</h1>
<p>Párrafo</p>
<img src="foto.jpg">

❌ No puedes inventar <producto> o <precio>

XML (tú defines las etiquetas):

<!-- Puedes crear las etiquetas que necesites -->
<producto>
  <nombre>Laptop</nombre>
  <precio moneda="EUR">899</precio>
  <enStock>true</enStock>
</producto>

✓ Defines etiquetas que tengan sentido para TU dominio

Analogía: Piensa en XML como un árbol genealógico donde:

  • El elemento raíz es el ancestro común (bisabuelo)
  • Los elementos hijos son descendientes directos (padres, hijos)
  • Los atributos son características de cada persona (edad, profesión)
  • La jerarquía muestra relaciones familiares (quién es padre de quién)

Tutorial paso a paso: Cómo crear tu primer XML desde cero

Aprenderás haciendo: Sigue estos pasos para crear un archivo XML que describa tu colección de música.

Paso 1: Crea un archivo de texto

Abre tu editor de texto favorito (Notepad++, VS Code, Sublime Text) y guarda el archivo como musica.xml

Paso 2: Añade la declaración XML

<?xml version="1.0" encoding="UTF-8"?>

¿Qué hace esto? Le dice al procesador XML qué versión usas (1.0) y qué codificación de caracteres (UTF-8 para soportar acentos y caracteres especiales).

Paso 3: Define el elemento raíz

<?xml version="1.0" encoding="UTF-8"?>
<coleccionMusical>

</coleccionMusical>

¿Por qué? Todo documento XML DEBE tener UN SOLO elemento raíz que contenga todo lo demás. Como el tronco de un árbol: todo sale de ahí.

Paso 4: Añade tu primer álbum

<?xml version="1.0" encoding="UTF-8"?>
<coleccionMusical>
  <album>
    <titulo>Abbey Road</titulo>
    <artista>The Beatles</artista>
    <anio>1969</anio>
  </album>
</coleccionMusical>

Observa: Las etiquetas se abren (<titulo>) y cierran (</titulo>) correctamente. La indentación NO es obligatoria, pero hace el código legible.

Paso 5: Añade más álbumes y usa atributos

<?xml version="1.0" encoding="UTF-8"?>
<coleccionMusical>
  <album formato="vinilo">
    <titulo>Abbey Road</titulo>
    <artista>The Beatles</artista>
    <anio>1969</anio>
    <genero>Rock</genero>
  </album>

  <album formato="CD">
    <titulo>Thriller</titulo>
    <artista>Michael Jackson</artista>
    <anio>1982</anio>
    <genero>Pop</genero>
  </album>
</coleccionMusical>

¿Atributo vs elemento? Usamos formato="vinilo" como atributo porque es una propiedad simple del álbum. El título es un elemento porque es el contenido principal.

¡Felicidades! Has creado tu primer XML válido y bien formado.

Sintaxis fundamental de XML

Un documento XML debe cumplir estas reglas para estar bien formado:

  • Declaración XML: (opcional pero recomendada) <?xml version="1.0" encoding="UTF-8"?>
  • Un único elemento raíz: todo el contenido debe estar dentro de un elemento principal
  • Etiquetas bien anidadas: las etiquetas se abren y cierran en orden correcto
  • Etiquetas cerradas: toda etiqueta abierta debe cerrarse (<nombre>...</nombre>) o ser autocerrada (<vacio/>)
  • Sensible a mayúsculas: <Libro> y <libro> son diferentes
  • Atributos entre comillas: <libro isbn="123"> no <libro isbn=123>

Ejemplos visuales de errores comunes

❌ ERROR 1: Etiqueta no cerrada

<libro>
  <titulo>Mi libro</titulo>
  <autor>Juan García
</libro>

Problema: La etiqueta <autor> no se cierra. XML dirá "not well-formed".

✓ CORRECTO:

<libro>
  <titulo>Mi libro</titulo>
  <autor>Juan García</autor>
</libro>

❌ ERROR 2: Anidamiento incorrecto

<libro>
  <titulo><enfasis>Gran libro</titulo></enfasis>
</libro>

Problema: Las etiquetas se cierran en orden incorrecto (se abre <enfasis> pero se cierra primero <titulo>).

✓ CORRECTO:

<libro>
  <titulo><enfasis>Gran libro</enfasis></titulo>
</libro>

❌ ERROR 3: Múltiples raíces

<?xml version="1.0"?>
<libro>
  <titulo>Libro 1</titulo>
</libro>
<libro>
  <titulo>Libro 2</titulo>
</libro>

Problema: Hay DOS elementos raíz (<libro>). XML solo permite UNO.

✓ CORRECTO:

<?xml version="1.0"?>
<biblioteca>
  <libro>
    <titulo>Libro 1</titulo>
  </libro>
  <libro>
    <titulo>Libro 2</titulo>
  </libro>
</biblioteca>

❌ ERROR 4: Atributos sin comillas

<libro isbn=123456>
  <titulo>Mi libro</titulo>
</libro>

Problema: El atributo isbn no tiene comillas.

✓ CORRECTO:

<libro isbn="123456">
  <titulo>Mi libro</titulo>
</libro>

❌ ERROR 5: Mayúsculas inconsistentes

<Libro>
  <titulo>Mi libro</titulo>
</libro>

Problema: Se abre <Libro> (mayúscula) pero se cierra </libro> (minúscula). XML es case-sensitive.

✓ CORRECTO:

<libro>
  <titulo>Mi libro</titulo>
</libro>

Errores comunes y cómo solucionarlos:

  • Si el XML no se abre/renderiza: Probablemente no está bien formado. Revisa etiquetas cerradas.
  • Si ves "parser error": Busca la línea indicada, suele ser una etiqueta mal cerrada.
  • Si dice "invalid": Está bien formado pero no cumple el esquema (DTD/XSD).
  • Truco: Usa un validador online como xmlvalidation.com para encontrar errores rápidamente.

Elementos vs Atributos

En XML puedes representar información de dos formas:

<!-- Usando elementos -->
<libro>
  <isbn>978-3-16-148410-0</isbn>
  <titulo>Aprendiendo XML</titulo>
</libro>

<!-- Usando atributos -->
<libro isbn="978-3-16-148410-0" titulo="Aprendiendo XML"/>

¿Cuándo usar elementos vs atributos?

  • Elementos: para datos complejos, contenido largo, o información que puede tener subelementos
  • Atributos: para metadatos simples, identificadores, o propiedades breves

Jerarquía en XML

XML permite crear estructuras jerárquicas (árbol de datos):

<?xml version="1.0" encoding="UTF-8"?>
<biblioteca>  <!-- Raíz -->
  <seccion nombre="Informática">  <!-- Nivel 1 -->
    <libro id="L001">  <!-- Nivel 2 -->
      <titulo>Estructuras de Datos</titulo>  <!-- Nivel 3 -->
      <autor>
        <nombre>Juan</nombre>  <!-- Nivel 4 -->
        <apellido>García</apellido>
      </autor>
      <precio moneda="EUR">45.00</precio>
    </libro>
  </seccion>
</biblioteca>

Validación con DTD

Analogía para entender DTD y XSD:

Imagina que XML es como rellenar un formulario. El DTD/XSD es como las instrucciones del formulario que te dicen:

  • Qué campos son obligatorios (nombre, apellidos)
  • Qué campos son opcionales (segundo apellido)
  • Qué tipo de datos debes poner (fecha de nacimiento debe ser una fecha, no texto)
  • En qué orden debes rellenarlos

Si no sigues las instrucciones, el formulario es inválido (aunque esté bien rellenado gramaticalmente).

¿Qué es un DTD?

Un DTD (Document Type Definition) define la estructura válida de un documento XML: qué elementos existen, en qué orden aparecen, cuántas veces pueden repetirse, y qué atributos tienen.

¿Por qué necesitas un DTD?

  • Control de calidad: Garantiza que todos los XML de tu sistema tengan la misma estructura
  • Comunicación: Si envías XML a otra empresa, el DTD es el "contrato" que especifica el formato
  • Validación automática: Los programas pueden rechazar XML mal formados antes de procesarlos
  • Documentación: El DTD documenta qué estructura esperas

Sintaxis básica de DTD

<!-- Declaración de elemento -->
<!ELEMENT nombre-elemento (contenido)>

<!-- Declaración de atributos -->
<!ATTLIST nombre-elemento
  nombre-atributo tipo-atributo valor-predeterminado
>

Tipos de contenido en DTD

  • (#PCDATA) - Texto plano (Parsed Character Data)
  • (elemento1, elemento2) - Secuencia ordenada de elementos
  • (elemento1 | elemento2) - Alternativa (uno u otro)
  • EMPTY - Elemento vacío
  • ANY - Cualquier contenido (evitar en producción)

Cardinalidades (cuántas veces aparece un elemento)

  • elemento - Exactamente una vez (1)
  • elemento? - Cero o una vez (0..1)
  • elemento* - Cero o más veces (0..n)
  • elemento+ - Una o más veces (1..n)

Ejemplo completo: Catálogo de productos con DTD

Archivo: catalogo.dtd

<!-- DTD para un catálogo de productos -->

<!-- Elemento raíz: debe contener uno o más productos -->
<!ELEMENT catalogo (producto+)>

<!-- Cada producto tiene: nombre, descripción, precio, y opcionalmente imagen -->
<!ELEMENT producto (nombre, descripcion, precio, imagen?)>

<!-- Atributos del producto -->
<!ATTLIST producto
  id        ID        #REQUIRED
  categoria CDATA     #REQUIRED
  stock     CDATA     #IMPLIED
>

<!-- Elementos simples de texto -->
<!ELEMENT nombre (#PCDATA)>
<!ELEMENT descripcion (#PCDATA)>
<!ELEMENT precio (#PCDATA)>
<!ELEMENT imagen EMPTY>

<!-- La imagen tiene URL como atributo -->
<!ATTLIST imagen
  url       CDATA     #REQUIRED
  alt       CDATA     #IMPLIED
>

Tutorial paso a paso: Crear tu primer DTD desde cero

Escenario: Quieres crear un sistema para gestionar recetas de cocina en XML.

Paso 1: Define qué estructura quieres en tu XML

Antes de escribir el DTD, piensa en la estructura. Una receta tiene:

  • Nombre de la receta (obligatorio)
  • Tiempo de preparación (obligatorio)
  • Lista de ingredientes (obligatorio, uno o más)
  • Pasos de preparación (obligatorio, uno o más)
  • Imagen (opcional)

Paso 2: Empieza por el elemento raíz

<!ELEMENT receta (nombre, tiempo, ingredientes, pasos, imagen?)>

¿Qué dice esto? Una <receta> DEBE contener (en este orden): nombre, tiempo, ingredientes, pasos, y OPCIONALMENTE una imagen (el ? significa "0 o 1 vez").

Paso 3: Define los elementos simples (texto)

<!ELEMENT nombre (#PCDATA)>
<!ELEMENT tiempo (#PCDATA)>

¿Qué es #PCDATA? Significa "texto plano" (Parsed Character Data). Estos elementos solo contienen texto.

Paso 4: Define elementos que contienen otros elementos

<!ELEMENT ingredientes (ingrediente+)>
<!ELEMENT ingrediente (#PCDATA)>

¿Qué significa el +? Significa "uno o más". Debe haber AL MENOS un ingrediente, pero puede haber más.

Paso 5: Define los pasos

<!ELEMENT pasos (paso+)>
<!ELEMENT paso (#PCDATA)>

Paso 6: Define elementos opcionales/vacíos

<!ELEMENT imagen EMPTY>
<!ATTLIST imagen
  url CDATA #REQUIRED
  alt CDATA #IMPLIED
>

¿Por qué EMPTY? La imagen no tiene contenido de texto, solo atributos (url y alt).
#REQUIRED = obligatorio | #IMPLIED = opcional

Paso 7: DTD completo

<!-- recetas.dtd -->
<!ELEMENT receta (nombre, tiempo, ingredientes, pasos, imagen?)>

<!ELEMENT nombre (#PCDATA)>
<!ELEMENT tiempo (#PCDATA)>

<!ELEMENT ingredientes (ingrediente+)>
<!ELEMENT ingrediente (#PCDATA)>

<!ELEMENT pasos (paso+)>
<!ELEMENT paso (#PCDATA)>

<!ELEMENT imagen EMPTY>
<!ATTLIST imagen
  url CDATA #REQUIRED
  alt CDATA #IMPLIED
>

Paso 8: Úsalo en tu XML

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE receta SYSTEM "recetas.dtd">
<receta>
  <nombre>Tortilla de patatas</nombre>
  <tiempo>30 minutos</tiempo>
  <ingredientes>
    <ingrediente>4 huevos</ingrediente>
    <ingrediente>3 patatas grandes</ingrediente>
    <ingrediente>Aceite de oliva</ingrediente>
    <ingrediente>Sal</ingrediente>
  </ingredientes>
  <pasos>
    <paso>Pelar y cortar las patatas en rodajas finas</paso>
    <paso>Freír las patatas en aceite abundante</paso>
    <paso>Batir los huevos y mezclar con las patatas</paso>
    <paso>Cuajar en la sartén por ambos lados</paso>
  </pasos>
  <imagen url="tortilla.jpg" alt="Tortilla de patatas española"/>
</receta>

¿Qué pasa si no cumples el DTD?

Ejemplos de XML que darían error:

  • ❌ Olvidar <nombre> → Error: elemento obligatorio faltante
  • ❌ Poner <tiempo> antes de <nombre> → Error: orden incorrecto
  • ❌ No poner ningún <ingrediente> → Error: se requiere al menos 1
  • ❌ Poner texto dentro de <imagen> → Error: debe ser EMPTY

Cuándo usar DTD

  • Para proyectos simples que solo necesitan validar estructura
  • Cuando trabajas con estándares antiguos (HTML 4.01, XHTML)
  • Si necesitas compatibilidad con sistemas legacy
  • Cuando la simplicidad es más importante que la validación avanzada

Limitaciones de DTD: No soporta tipos de datos (todo es texto), no tiene namespaces nativos, sintaxis diferente a XML, y no permite restricciones avanzadas. Para proyectos modernos, usa XSD.

Validación con XSD (XML Schema)

¿Qué es XSD?

XSD (XML Schema Definition) es el estándar moderno para validar XML. A diferencia de DTD, XSD está escrito en XML, soporta tipos de datos (números, fechas, booleanos), permite restricciones avanzadas (rangos, patrones regex), y maneja namespaces de forma nativa.

Tipos de datos en XSD

Tipo Descripción Ejemplo
xs:string Cadena de texto "Hola mundo"
xs:integer Número entero 42, -17
xs:decimal Número decimal 3.14, 99.99
xs:boolean Verdadero/Falso true, false
xs:date Fecha (YYYY-MM-DD) 2024-01-15
xs:time Hora (HH:MM:SS) 14:30:00
xs:dateTime Fecha y hora 2024-01-15T14:30:00
xs:gYear Año (YYYY) 2024

Elementos en XSD

<!-- Elemento simple con tipo predefinido -->
<xs:element name="nombre" type="xs:string"/>
<xs:element name="edad" type="xs:integer"/>
<xs:element name="precio" type="xs:decimal"/>

<!-- Elemento con valor predeterminado -->
<xs:element name="idioma" type="xs:string" default="es"/>

<!-- Elemento opcional -->
<xs:element name="comentario" type="xs:string" minOccurs="0"/>

<!-- Elemento repetible -->
<xs:element name="etiqueta" type="xs:string" maxOccurs="unbounded"/>

Atributos en XSD

<!-- Atributo requerido -->
<xs:attribute name="id" type="xs:string" use="required"/>

<!-- Atributo opcional -->
<xs:attribute name="activo" type="xs:boolean" use="optional"/>

<!-- Atributo con valor por defecto -->
<xs:attribute name="idioma" type="xs:string" default="es"/>

Restricciones (Facets)

XSD permite restringir valores con facets:

<!-- Restricción de longitud de texto -->
<xs:simpleType name="codigoPostalType">
  <xs:restriction base="xs:string">
    <xs:length value="5"/>  <!-- Exactamente 5 caracteres -->
  </xs:restriction>
</xs:simpleType>

<!-- Restricción de rango numérico -->
<xs:simpleType name="edadType">
  <xs:restriction base="xs:integer">
    <xs:minInclusive value="18"/>
    <xs:maxInclusive value="65"/>
  </xs:restriction>
</xs:simpleType>

<!-- Restricción con patrón (regex) -->
<xs:simpleType name="telefonoType">
  <xs:restriction base="xs:string">
    <xs:pattern value="\d{3}-\d{3}-\d{3}"/>  <!-- 123-456-789 -->
  </xs:restriction>
</xs:simpleType>

<!-- Enumeración (valores permitidos) -->
<xs:simpleType name="estadoType">
  <xs:restriction base="xs:string">
    <xs:enumeration value="pendiente"/>
    <xs:enumeration value="procesando"/>
    <xs:enumeration value="completado"/>
    <xs:enumeration value="cancelado"/>
  </xs:restriction>
</xs:simpleType>

<!-- Múltiples restricciones combinadas -->
<xs:simpleType name="usernameType">
  <xs:restriction base="xs:string">
    <xs:minLength value="3"/>
    <xs:maxLength value="20"/>
    <xs:pattern value="[a-zA-Z0-9_]+"/>  <!-- Solo letras, números y _ -->
  </xs:restriction>
</xs:simpleType>

Tutorial paso a paso: Crear tu primer XSD desde cero

Escenario: Quieres crear un esquema XSD para validar información de estudiantes.

Ventaja de XSD sobre DTD: Mientras DTD solo verifica estructura, XSD puede validar que la edad sea un número entero, el email tenga formato válido, y la nota esté entre 0 y 10.

Paso 1: Estructura básica del XSD

<?xml version="1.0" encoding="UTF-8"?>
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">

  <!-- Aquí irán las definiciones -->

</xs:schema>

¿Qué es xmlns:xs? Es el namespace (espacio de nombres) de XML Schema. El prefijo "xs:" indica que es parte del estándar XSD.

Paso 2: Define el elemento raíz

<xs:element name="estudiante">
  <xs:complexType>
    <xs:sequence>
      <!-- Los elementos hijos irán aquí -->
    </xs:sequence>
  </xs:complexType>
</xs:element>

¿Qué significa esto?
• complexType = el elemento contiene otros elementos (no solo texto)
• sequence = los elementos hijos deben aparecer EN ORDEN

Paso 3: Añade elementos simples con tipos de datos

<xs:element name="estudiante">
  <xs:complexType>
    <xs:sequence>
      <xs:element name="nombre" type="xs:string"/>
      <xs:element name="edad" type="xs:integer"/>
      <xs:element name="email" type="xs:string"/>
      <xs:element name="nota" type="xs:decimal"/>
    </xs:sequence>
  </xs:complexType>
</xs:element>

Ahora XSD validará: que "edad" sea un número entero, "nota" sea un decimal, etc.

Paso 4: Añade restricciones (lo potente de XSD)

<?xml version="1.0" encoding="UTF-8"?>
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">

  <xs:element name="estudiante">
    <xs:complexType>
      <xs:sequence>
        <!-- Nombre: mínimo 2 caracteres -->
        <xs:element name="nombre">
          <xs:simpleType>
            <xs:restriction base="xs:string">
              <xs:minLength value="2"/>
            </xs:restriction>
          </xs:simpleType>
        </xs:element>

        <!-- Edad: entre 16 y 99 años -->
        <xs:element name="edad">
          <xs:simpleType>
            <xs:restriction base="xs:integer">
              <xs:minInclusive value="16"/>
              <xs:maxInclusive value="99"/>
            </xs:restriction>
          </xs:simpleType>
        </xs:element>

        <!-- Email: patrón básico de validación -->
        <xs:element name="email">
          <xs:simpleType>
            <xs:restriction base="xs:string">
              <xs:pattern value="[^@]+@[^@]+\.[^@]+"/>
            </xs:restriction>
          </xs:simpleType>
        </xs:element>

        <!-- Nota: entre 0 y 10 con 2 decimales -->
        <xs:element name="nota">
          <xs:simpleType>
            <xs:restriction base="xs:decimal">
              <xs:minInclusive value="0"/>
              <xs:maxInclusive value="10"/>
              <xs:fractionDigits value="2"/>
            </xs:restriction>
          </xs:simpleType>
        </xs:element>
      </xs:sequence>

      <!-- Atributo ID obligatorio -->
      <xs:attribute name="id" type="xs:string" use="required"/>
    </xs:complexType>
  </xs:element>

</xs:schema>

Paso 5: XML válido según este XSD

<?xml version="1.0" encoding="UTF-8"?>
<estudiante id="E001"
  xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:noNamespaceSchemaLocation="estudiante.xsd">
  <nombre>María García</nombre>
  <edad>20</edad>
  <email>maria@example.com</email>
  <nota>8.75</nota>
</estudiante>

Ejemplos de validación: qué pasa cuando NO cumples las reglas

❌ Ejemplo 1: Edad fuera de rango

<edad>15</edad>  <!-- ERROR: debe ser ≥ 16 -->

Error de validación: "Value '15' is not facet-valid with respect to minInclusive '16'"

❌ Ejemplo 2: Email sin formato correcto

<email>maria.correo.mal</email>  <!-- ERROR: falta @ y dominio -->

Error de validación: "Value does not match pattern '[^@]+@[^@]+\.[^@]+'"

❌ Ejemplo 3: Nota con demasiados decimales

<nota>8.759</nota>  <!-- ERROR: solo se permiten 2 decimales -->

Error de validación: "Value '8.759' has too many fraction digits (max 2)"

❌ Ejemplo 4: Tipo de dato incorrecto

<edad>veinte</edad>  <!-- ERROR: debe ser un número -->

Error de validación: "'veinte' is not a valid value of the atomic type 'xs:integer'"

Poder de XSD: Con DTD, la edad podría ser "veinte" y sería válido (porque DTD solo ve texto). Con XSD, puedes garantizar que sea un número, esté en un rango específico, y tenga el formato correcto.

Comparativa DTD vs XSD

Característica DTD XSD
Sintaxis Propia (no XML) XML estándar
Tipos de datos Solo texto (PCDATA, CDATA) Múltiples (string, integer, date, boolean, etc.)
Restricciones Muy limitadas (enumeraciones básicas) Avanzadas (rangos, patrones, longitudes)
Namespaces No soportados nativamente Soporte completo
Herencia No Sí (extends, restricts)
Complejidad Simple Más complejo pero más potente
Uso actual Legacy, HTML 4.01, XHTML Estándar moderno, configuraciones empresariales
Validación Solo estructura Estructura + contenido + tipos

Recomendación: Para proyectos nuevos, usa siempre XSD. Solo usa DTD si trabajas con sistemas legacy o estándares antiguos que lo requieran específicamente.

Namespaces en XML

¿Qué son los namespaces?

Los namespaces (espacios de nombres) permiten evitar conflictos cuando mezclamos vocabularios XML de diferentes fuentes. Por ejemplo, si usas elementos de XHTML y SVG en el mismo documento, ambos podrían tener un elemento <title> con significados diferentes.

Sintaxis de namespaces

<!-- Declarar namespace con prefijo -->
<elemento xmlns:prefijo="http://ejemplo.com/namespace">
  <prefijo:subelemento>contenido</prefijo:subelemento>
</elemento>

<!-- Namespace por defecto (sin prefijo) -->
<elemento xmlns="http://ejemplo.com/namespace">
  <subelemento>contenido</subelemento>
</elemento>

Ejemplo práctico: Mezclando XHTML y SVG

<?xml version="1.0" encoding="UTF-8"?>
<html xmlns="http://www.w3.org/1999/xhtml">
  <head>
    <title>Página con SVG embebido</title>
  </head>
  <body>
    <h1>Gráfico SVG</h1>

    <!-- SVG con su propio namespace -->
    <svg xmlns="http://www.w3.org/2000/svg" width="200" height="200">
      <circle cx="100" cy="100" r="50" fill="blue"/>
      <!-- Este 'title' es de SVG, no de XHTML -->
      <title>Círculo azul</title>
    </svg>

    <p>Texto después del gráfico</p>
  </body>
</html>

Ejemplo: Documento XML con múltiples namespaces

<?xml version="1.0" encoding="UTF-8"?>
<doc:documento
    xmlns:doc="http://ejemplo.com/documento"
    xmlns:meta="http://ejemplo.com/metadatos"
    xmlns:cont="http://ejemplo.com/contenido">

  <!-- Metadatos usando el prefijo 'meta' -->
  <meta:informacion>
    <meta:autor>Ana García</meta:autor>
    <meta:fecha>2024-01-15</meta:fecha>
    <meta:version>1.0</meta:version>
  </meta:informacion>

  <!-- Contenido usando el prefijo 'cont' -->
  <cont:cuerpo>
    <cont:seccion id="intro">
      <cont:titulo>Introducción</cont:titulo>
      <cont:parrafo>Este es el contenido principal.</cont:parrafo>
    </cont:seccion>
  </cont:cuerpo>

</doc:documento>

Buena práctica: Usa namespaces cuando combines vocabularios XML diferentes (SOAP + datos propios, XHTML + SVG + MathML, etc.). Para documentos XML simples de un solo vocabulario, no son necesarios.

En resumen: XML - Conceptos clave

Lo que DEBES saber para el examen/proyecto:

1. Estructura de XML:

  • XML es extensible: tú defines las etiquetas
  • Debe tener un único elemento raíz
  • Etiquetas case-sensitive: <Libro> ≠ <libro>
  • Todas las etiquetas deben cerrarse correctamente
  • Atributos siempre entre comillas

2. Bien formado vs Válido:

  • Bien formado = cumple reglas sintácticas de XML (obligatorio)
  • Válido = cumple reglas de un esquema DTD/XSD (opcional pero recomendado)

3. DTD vs XSD:

  • DTD: simple, solo valida estructura, sintaxis propia
  • XSD: potente, valida tipos de datos y contenido, escrito en XML
  • Usa XSD en proyectos modernos (puede validar que edad sea número, email tenga formato correcto, etc.)

4. Usos reales:

  • Configuración: Maven (pom.xml), Spring, Android (AndroidManifest.xml)
  • Intercambio de datos: SOAP, RSS, APIs legacy
  • Documentos: SVG (gráficos vectoriales), XHTML

5. Errores comunes a evitar:

Preguntas de autoevaluación

Pregunta 1: ¿Por qué este XML NO está bien formado?

<biblioteca>
  <libro>
    <titulo>El Quijote</Titulo>
  </libro>
Ver respuesta

La etiqueta se abre como <titulo> (minúscula) pero se cierra como </Titulo> (con T mayúscula). XML es case-sensitive, por lo que esto es un error. Además, falta cerrar </biblioteca>.

Pregunta 2: ¿Cuál es la diferencia principal entre DTD y XSD?

Ver respuesta

DTD solo valida la estructura (qué elementos existen, en qué orden), mientras que XSD además valida tipos de datos (puede verificar que un campo sea un número, una fecha, esté en un rango, etc.). XSD está escrito en XML, DTD usa su propia sintaxis.

Pregunta 3: Si tienes un XML bien formado pero sin DTD/XSD, ¿es válido?

Ver respuesta

Técnicamente, si no hay DTD/XSD, no se puede hablar de "válido" o "inválido", solo de "bien formado". La validación solo tiene sentido cuando existe un esquema contra el cual validar.

Pregunta 4: ¿En qué situación usarías XML en lugar de JSON?

Ver respuesta

XML es preferible cuando necesitas:

  • Validación estricta con esquemas (XSD)
  • Documentos complejos con metadatos (atributos + elementos)
  • Compatibilidad con sistemas legacy
  • Estándares específicos (SOAP, RSS, SVG)
  • Procesamiento con XSLT/XPath
JSON es mejor para APIs REST modernas, configuración simple, y cuando la velocidad/simplicidad importan más que la validación estricta.

¿Qué es Markdown?

Markdown es un lenguaje de marcado ligero creado en 2004 por John Gruber y Aaron Swartz. Su filosofía es simple: el texto debe ser fácil de leer incluso en formato plano, sin necesidad de procesarlo. Markdown se convierte fácilmente a HTML, PDF, y otros formatos.

Ventaja clave: Un archivo Markdown (.md) es perfectamente legible como texto plano, pero puede renderizarse con formato rico en navegadores, editores, y plataformas como GitHub.

  • Formato se rompe entre versiones
  • Pesado (varios MB por documento)
  • Necesitas el programa instalado
  • Difícil de automatizar
  • Se corrompe con el tiempo

✅ Ventajas de Markdown:

  • Archivos de texto plano (versionables)
  • Nunca se rompe el formato
  • Ligero (pocos KB)
  • Abres con cualquier editor
  • Fácil de automatizar (scripts, CI/CD)
  • Nunca se corrompe

Realidad profesional: En desarrollo de software, NUNCA uses Word para documentación técnica. Usa Markdown. Es el estándar de facto en GitHub, GitLab, Stack Overflow, Reddit, Discord, y prácticamente toda la industria tech.

La prioridad de una tarea se calcula con la fórmula:

## Fórmula de cálculo de precio

El precio de una reserva se calcula:

$$
P_{total} = \sum_{i=1}^{n} P_{noche} \times (1 - D_i)
$$

Donde:
- $P_{noche}$ = Precio base por noche
- $D_i$ = Descuento aplicable el día $i$
- $n$ = Número de noches

¿Qué es LaTeX?

LaTeX (pronunciado "la-tek" o "lay-tek") es un sistema de composición de documentos de alta calidad tipográfica, especialmente diseñado para producir documentación científica y técnica. Fue creado por Leslie Lamport en 1985 basándose en TeX de Donald Knuth.

A diferencia de procesadores de texto WYSIWYG (como Word), LaTeX es un lenguaje de marcado donde describes la estructura lógica del documento y el sistema se encarga del formato y composición visual.

Analogía clave: LaTeX es a los documentos lo que HTML+CSS es a las páginas web. Tú defines la estructura (LaTeX) y el sistema aplica el estilo profesional automáticamente.

¿Cuándo necesitas LaTeX? Decisión práctica

Usa LaTeX si necesitas:

  • ✅ Fórmulas matemáticas complejas (ecuaciones, matrices, integrales)
  • ✅ Documentos académicos (papers, tesis, artículos científicos)
  • ✅ Bibliografías y citas automáticas (BibTeX)
  • ✅ Numeración automática de secciones, figuras, tablas, ecuaciones
  • ✅ Tipografía perfecta (kerning, justificación, guiones automáticos)
  • ✅ Formato consistente en documentos largos (100+ páginas)
  • ✅ Trabajo colaborativo versionable (archivos de texto plano + Git)

Usa Word/LibreOffice si necesitas:

  • ⚠️ Documentos simples con poco formato
  • ⚠️ Colaboración con personas no técnicas
  • ⚠️ Edición visual rápida (ver resultado inmediato)
  • ⚠️ Gráficos y diagramas simples

Los algoritmos de ordenación son fundamentales en informática.
En este documento analizaremos \textbf{tres algoritmos básicos}:

\section{Bubble Sort}

\subsection{Descripción}
Bubble Sort compara elementos adyacentes y los intercambia si están
en el orden incorrecto. El algoritmo repite este proceso hasta que
la lista está ordenada.

\subsection{Complejidad}
La complejidad temporal de Bubble Sort es:

\begin{equation}
  O(n^2) \text{ en el peor caso}
\end{equation}

Donde $n$ es el número de elementos.

\subsection{Pseudocódigo}
\begin{verbatim}
para i = 0 hasta n-1:
    para j = 0 hasta n-i-1:
        si array[j] > array[j+1]:
            intercambiar(array[j], array[j+1])
\end{verbatim}

\section{Comparativa de algoritmos}

\begin{table}[h]
\centering
\caption{Comparativa de complejidad temporal}
\begin{tabular}{|l|c|c|c|}
\hline
\textbf{Algoritmo} & \textbf{Mejor caso} & \textbf{Caso promedio} & \textbf{Peor caso} \\
\hline
Bubble Sort  & $O(n)$       & $O(n^2)$     & $O(n^2)$     \\
Selection Sort & $O(n^2)$   & $O(n^2)$     & $O(n^2)$     \\
Quick Sort   & $O(n \log n)$ & $O(n \log n)$ & $O(n^2)$   \\
\hline
\end{tabular}
\end{table}

\section{Conclusión}
Quick Sort es generalmente el más eficiente para grandes conjuntos
de datos, aunque en el peor caso tiene complejidad $O(n^2)$.

JSON (JavaScript Object Notation)

¿Por qué los programadores odian XML y prefieren JSON?

El problema de XML:

<?xml version="1.0"?>
<respuesta>
  <estado>exito</estado>
  <datos>
    <usuario>
      <id>123</id>
      <nombre>Ana</nombre>
    </usuario>
  </datos>
</respuesta>

❌ 12 líneas de código
❌ Muy verbose (repetición de etiquetas)
❌ Difícil de parsear en JavaScript
❌ Ocupa más bytes (más lento de transmitir)

La solución: JSON

{
  "estado": "exito",
  "datos": {
    "usuario": {
      "id": 123,
      "nombre": "Ana"
    }
  }
}

✅ 9 líneas de código
✅ Compacto y legible
✅ Se parsea directamente en JavaScript con JSON.parse()
✅ Menor tamaño (respuestas más rápidas)

Dato histórico: JSON fue creado por Douglas Crockford en 2001. En 2006, Google, Facebook y Twitter comenzaron a usarlo en sus APIs. Hoy, JSON es el estándar de facto para APIs REST, reemplazando casi completamente a XML.

¿Qué es JSON?

JSON es un formato ligero de intercambio de datos, fácil de leer y escribir para humanos y fácil de parsear y generar para máquinas. Aunque nació de JavaScript, es independiente del lenguaje.

YAML (YAML Ain't Markup Language)

¿Qué es YAML?

YAML es un formato de serialización de datos legible por humanos, diseñado para ser más amigable que JSON o XML. Es especialmente popular en configuración de DevOps.

Advertencia importante sobre YAML:

YAML usa INDENTACIÓN (espacios) para definir la estructura. Si mezclas espacios y tabs, o usas la indentación incorrecta, el archivo será inválido. Siempre usa espacios, nunca tabs.

Explicar indentación en YAML como si nunca lo hubieran visto

🔑 Concepto clave: La indentación crea jerarquía

En JSON usas llaves {} para agrupar. En YAML usas espacios al inicio de la línea:

JSON (con llaves):

{
  "persona": {
    "nombre": "Ana"
  }
}

YAML (con espacios):

persona:
  nombre: Ana

↑ 2 espacios = "dentro de persona"

Reglas de oro de la indentación:

  1. Usa siempre espacios (nunca tabs). Recomendado: 2 espacios por nivel.
  2. Mismo nivel = misma indentación
  3. Nivel hijo = 2 espacios más que el padre
  4. Mezclar espacios y tabs = ERROR

Ejemplo visual con niveles:

aplicacion:              # Nivel 0 (ningún espacio)
  nombre: Mi App         # Nivel 1 (2 espacios) - dentro de "aplicacion"
  version: 1.0           # Nivel 1 (2 espacios) - dentro de "aplicacion"
  configuracion:         # Nivel 1 (2 espacios) - dentro de "aplicacion"
    puerto: 8080         # Nivel 2 (4 espacios) - dentro de "configuracion"
    host: localhost      # Nivel 2 (4 espacios) - dentro de "configuracion"
    database:            # Nivel 2 (4 espacios) - dentro de "configuracion"
      motor: PostgreSQL  # Nivel 3 (6 espacios) - dentro de "database"
      puerto: 5432       # Nivel 3 (6 espacios) - dentro de "database"

❌ ERROR COMÚN: Indentación incorrecta

persona:
nombre: Ana       # ❌ MALO: debería tener 2 espacios
  edad: 25        # ❌ MALO: no está alineado con "nombre"

✅ CORRECTO:

persona:
  nombre: Ana     # ✅ BIEN: 2 espacios
  edad: 25        # ✅ BIEN: alineado con "nombre"

Buenas prácticas generales

1. Separación de configuración

  • Variables de entorno en .env (no commitear)
  • Configuración de desarrollo en archivos locales
  • Configuración de producción en variables de entorno del servidor

2. Versionado de configuración

  • Commitea archivos de configuración de estructura (package.json, docker-compose.yml)
  • NO commitees secretos (usa .gitignore)
  • Documenta variables de entorno requeridas en README

3. Documentación como código

  • README.md en raíz siempre actualizado
  • Documentación de API en Markdown o OpenAPI (YAML)
  • CHANGELOG.md para seguimiento de versiones
  • Comentarios en archivos de configuración complejos

4. Validación

  • Valida JSON con herramientas online o linters
  • Usa schemas JSON Schema para APIs
  • Valida YAML antes de deployar (CI/CD puede fallar)
  • Formatea automáticamente con Prettier/Black/etc

Consejo profesional: Crea plantillas de proyecto (boilerplates) con todos los archivos de configuración ya preparados. Muchos frameworks ofrecen CLIs que generan scaffolding automáticamente: create-react-app, vue create, rails new, etc.

Ejercicio 4: DTD para validación

Tarea: Diseña un DTD para validar un documento XML de un restaurante.

  • Cada plato tiene: nombre, descripción, precio, y opcionalmente alérgenos
  • Precio debe tener atributo de moneda (EUR, USD, GBP)

Luego crea un XML válido contra ese DTD.

Ejercicio 5: XSD con restricciones

Tarea: Crea un XSD para validar pedidos de una tienda online.

Restricciones:

  • ID de pedido: formato PED-YYYY-NNNN (regex)
  • Email del cliente: validar formato
  • Teléfono: formato +XX XXX XXX XXX
  • Cantidad de productos: mínimo 1
  • Precio: decimal con 2 decimales, mínimo 0
  • Estado: enumeración (pendiente, procesando, enviado, entregado)
  • Fecha: tipo xs:date

Crea también un XML de ejemplo que sea válido.
